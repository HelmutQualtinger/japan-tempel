# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A scratch directory (`Playground/`, inside the parent `training` repo, which has its own CLAUDE.md for the unrelated cycling log). It currently holds one file: `tempel.html`, a self-contained, navigable three.js scene of a Japanese temple. No build system, no package manager, no tests.

## Running

`tempel.html` loads three.js as ES modules via an `importmap` pointing at `cdn.jsdelivr.net` (three@0.186.1: `three` and `three/webgpu` → `three.webgpu.js`, `three/tsl` → `three.tsl.js`, addons from `examples/jsm`), so it needs internet and must be served over HTTP, not opened via `file://`:

```bash
python3 -m http.server 8757   # from this directory; avoid port 5000 (macOS AirPlay)
# then open http://localhost:8757/tempel.html
```

Published via GitHub Pages at https://helmutqualtinger.github.io/japan-tempel/ (`index.html` redirects to `tempel.html`). Both pages carry Open Graph/Twitter tags pointing at `preview.jpg` (1200×630 screenshot with title overlay) — retake it when the scene changes noticeably.

**PWA (installable on Android and iOS, offline-capable):** `manifest.webmanifest` (start_url `tempel.html`, `display: fullscreen`, icons `icon-192.png`/`icon-512.png`/`icon-maskable-512.png` — a torii drawn with Pillow), iOS extras in the `<head>` of `tempel.html` (`apple-touch-icon.png` 180×180, `apple-mobile-web-app-*` metas; `black-translucent` status bar + `viewport-fit=cover`, so `#hud`/`#btns` are offset by `env(safe-area-inset-*)`) and `sw.js`, registered by an inline script in `tempel.html`. The service worker precaches the local files plus the three.js CDN modules; same-origin requests are network-first (cache fallback), CDN requests cache-first. When changing the three.js version or adding an `three/addons` import or a new local asset, update the `CDN`/`REMOTE`/`LOCAL` lists in `sw.js` and bump `CACHE` (`tempel-v5`), otherwise the app breaks offline.

## Architecture of tempel.html

Everything is one `<script type="module">`, top to bottom in dependency order — later sections reference helpers and materials defined earlier, so keep that order when inserting code:

**Renderer:** `THREE.WebGPURenderer` (WebGPU where available, automatic WebGL 2 fallback; `?webgl` in the URL forces WebGL 2; the backend in use is appended to the `#hud` text). The script does `await renderer.init()` before anything uses the renderer (`PMREMGenerator.fromScene` for the Tesla). `ShaderMaterial`, `onBeforeCompile` and `customDepthMaterial` don't work with this renderer: all custom shading is TSL (`three/tsl` imports) on node materials (`MeshStandardNodeMaterial` via `stdN()`, `MeshBasicNodeMaterial`, `LineBasicNodeMaterial`), with uniforms as `uniform()` nodes (set `.value`). Plain `MeshStandardMaterial` etc. are converted automatically. Use `smoothstep(lo,hi,x)` only with lo<hi (WGSL), and the hand-written GLSL-style `mod` where arguments can be negative. Shadows are `PCFShadowMap` (no PCFSoft in WebGPU); time comes from `clock` = `THREE.Timer` (`clock.update()` in the loop, `clock.getElapsed()`).

1. **Scene/camera/OrbitControls/lights** (`hemi`, `sun` with shadows).
2. **Textures + materials.** All textures are generated procedurally on a `<canvas>` (`canvasTex`, `woodDraw`, `speckle`, with a local seeded `trnd`) — the only image file is `face.png` (Carl's face). Materials live in the `M` object. `M.<x>.userData.tile` (world units per texture tile) and `.grain` drive UV scaling in `box()`. `cyl()` swaps `M.wood`/`M.dark` for `M.woodC`/`M.darkC` (cloned textures with their own repeat) because box UVs are rescaled to world size but cylinder UVs are not.
3. **Geometry helpers** (`mesh`, `box`, `cyl`) — `box()` rewrites UVs per face; `roofGeometry()` builds the curved hip roof as a heightfield (concave profile + lifted corners) with world-scale UVs. `bake(g)` merges all meshes of a static group into one mesh per material/castShadow/renderOrder (same material objects, so `applyLight()` still works; lights stay) — used on hall, tower, castle, torii, lanterns, bridge and Tesla, because the WebGPURenderer's shadow pass costs a lot of CPU per object. Don't keep references to individual meshes of a baked group; animate via materials or keep the part out of the group. Right before the render loop, every mesh whose world-space bounding radius is < 0.2 gets `castShadow=false` (eyes, hooves, rotors …).
4. **Buildings** (main hall, Tokyo Tower in place of the former pagoda — `tokyoTower()`, lattice of `beam()` boxes along a width profile, painted in orange/white height bands, footprint in `TOWER` — a scaled-down Osaka Castle keep right of the hall — `osakaCastle()`, footprint in `CASTLE`; `keepClear` lists areas random trees must skip — torii, stone lanterns, pond/bridge, trees), a parked **Tesla** (`makeTesla`: extruded side profile built in metres, scaled ×2; `CAR` holds its footprint, which `navBlocked` uses; its paint/glass/chrome use a `RoomEnvironment` PMREM `envMap` on those materials only, and `applyLight()` drives its lamps and reflection strength. `ExtrudeGeometry` bevels grow the body ~0.07 beyond the profile, so surface details are placed against that offset), then **animals** (`makeDeer`/`updateDeer`, `makeGiraffe`/`updateGiraffe`). A quadcopter **drone** (`makeDrone`/`updateDrone`) escorts Carl, easing toward a point `drone.above` (8 units ≈ 4 m) over his head and climbing over the hall roof, tower and trees via `droneCeiling()`. Animals are built facing +Z and move along closed `CatmullRomCurve3` loops (`getPointAt`/`getTangentAt`), with leg/neck swing driven by a phase counter. Loop waypoints are hand-picked to avoid buildings and the pond; re-check them if you move scenery.
   **Carl** (`makeCarl`/`updateCarl`) is a jointed figure (hips/knees, shoulders/elbows) whose face is `face.png`. The head is a sphere pulled onto a skull shape by `headPt()` via `headGeo(k,…)`, where `k(x,y,z)` is the shell offset: skull (skin + hair + beard texture), a photo shell projected from the front whose vertex alpha fades it out towards the sides (so it doesn't smear there), and an alpha-tested hair cap (base 1.024, above the photo shell so the photo never shows through it). Proportions are measured from `face.png` (whose background is transparent): `R`, `PS` (head side ↔ photo x=±0.8) and `toM()` map head coordinates to un-tilted photo coordinates `m`; `photoUV()` adds the photo's ~4.5° roll and the lower face's slight turn. `relief(mx,my)` adds nose, eye sockets, brows, cheekbones, lips and chin as Z offsets at their photo positions (listed in its comment), plus a square beard jaw, a chin pushed forward and a back of the head ending above the nape; normals are computed numerically in `headGeo` so the relief shades. 3D ears and glasses temples (from the photo's frame hinges back over the ears) sit at the photo's positions — re-measure all of this if `face.png` is replaced. Hair is one canvas (`hairCv`, strands in colours sampled from the photo, own generator `hrnd`) drawn in sphere UVs; `hairY(a)` gives the hairline height over the angle from the view direction (forehead, above the ears, nape) and drives both the texture and the cap thickness. `carlGlow` materials get a small emissive so the face reads like the photo. His loop runs down the centre of the lantern avenue (lanterns at x=±3.4), back on the pond side, across the bridge, up the hall steps, once around the hall on the stone plinth (the strip between the engawa and the plinth edge) and down the steps again. `groundY(x,z)` supplies his height from the top surfaces of the geometry (grass 0, gravel yard 0.2, stone path 0.25 / slabs 0.295, hall plinth 1.7, steps as a ramp, pond rim + bridge plank arc) — keep it in sync when any of those move. The `#speedIn` slider sets `carl.speed` (0–14); `updateCarl` derives `run` (0 = walk, 1 = jog, reached at 3.2) and `sp` (0 = jog, 1 = sprint, reached at 10.2) from it and scales swing, stride length, knee/elbow bend, kick, lean, flight, dust and step volume. `updateCarl` plants the lowest foot on the ground each frame and calls `puff()` (`dust`: one instanced billboard mesh whose `dustMat` `vertexNode` (TSL) integrates each puff from `aStart`/`aVel`/`aLife` = birth, duration, size; `puff()` only writes instance data, `updateDust` only sets uniforms) on every footstrike where `onGravel()` is true (i.e. `groundY` returns the yard height). Each footstrike also calls `stepSound(surfaceAt(x,z), vol)` (Web Audio noise bursts per surface: grass/gravel/stone/wood, quieter with camera distance); its `AudioContext` (`sfx`) starts on the first pointerdown/keydown and is separate from the music's. Carl has two modes: `'loop'` (the curve above) and `'free'` (walks `carl.path` to a clicked goal, then stands; `carl.move` eases the gait to a standing pose). A click (pointer up without drag, only when not following) goes `pickGround()` (ray-march against `groundY`) → `sendCarl()` → `findPath()`. Turning follow on calls `resumeLoop()`, which walks him to the nearest loop point on his level and re-enters the curve. A spotted hyena (`chaser`/`updateChaser`; built by `makeHyena()`, materials in `HY` with canvas fur textures from their own generator, seed 13) trails him. Its torso, neck and head are `loft()` meshes (ellipse cross-sections along a `CatmullRomCurve3`, profile from `keyProf([[t,w,h,dy],…])`, uv u around / v along); it has the same rig as `makeDeer` (faces +Z, `userData` `legs`/`neck`/`head`) plus `knees` (elbow/hock pivots with `userData.base`, bent while a leg swings forward) and `tail`. Each rigid part is `bake()`d separately before child pivots are attached, so the joints stay movable. The front legs are longer than the hind legs (sloping back) by consuming `carl.trail` (breadcrumbs of Carl's actual positions) `gap` units behind, so it takes the same obstacle-free route in both modes; it is pitched to the ground under its legs and offset sideways only on open ground.
   **Navigation** (section after `groundY`): a 0.5-unit grid (`navOk`/`navY`/`navReach`) with A* (`findPath`, smoothed by `navSight`). `navBlocked()` hard-codes hall, plinth wall, tower and castle footprints, pond (bridge corridor stays free), lanterns and torii posts, plus `obstacles` (trees push `[x,z,r]` when created). Steps between cells are allowed only if the `groundY` difference is ≤ `NAV_STEP`, which is what forces routes onto the stairs and the bridge. The grid is built once at load — moving scenery means updating `navBlocked`/`groundY`. `#carlBtn` toggles `follow` (`updateFollow` keeps the camera in front of him each frame, preserving the user's zoom distance and height but overriding horizontal orbit). `#gyroBtn` ("Neigung", shown only on touch devices with `DeviceOrientationEvent`; auto-on on Android, needs a tap on iOS for `requestPermission`) feeds device yaw/pitch deltas (`onTilt` → `updateGyro`) into the orbit around `controls.target`, on top of touch drag; in follow mode only the pitch survives.
5. **Rain** (`LineSegments` of 8000 drops with a `LineBasicNodeMaterial`, uniforms in `rainU`: the buffer holds static start points, its `positionNode` does fall, wind and wrapping in a box around `uCam`; `raining`/`rainB` blend) and **day/night** (`night`/`blend`); both feed `applyLight()`, which blends sky color, fog, `hemi`/`sun` intensity, lantern emissive and the `PointLight`s in `lampLights` (intensity `night blend × userData.k`) each frame. Only 6 PointLights exist (the two big hall lanterns + four over the avenue centre; the 14 avenue lanterns only glow via `M.glow`, `lantern(false)`), because every light costs fragment time in every lit material even at intensity 0, and toggling lights/shadows at runtime makes WebGPU rebuild all pipelines (multi-second freeze) — keep the light count fixed and small. The renderer's pixel ratio is capped at 1.5 for the same GPU reason. Buttons (`#rainBtn`, `#dayBtn`, `#rotBtn`) just flip these flags and mirror them in `aria-pressed`.
   **Sky dome** (`sky`/`skyMat`, declared right after `applyLight`): a camera-centred `MeshBasicNodeMaterial` sphere (TSL `colorNode`, uniforms in `skyU`; `hash`/`noise`/`fbm3`/`fbm4`/`fbm5` (from `fbmN(octaves)`)/`clouds` are `Fn(...).setLayout()` functions; `clouds` returns density plus a density sample shifted towards the sun for the lighting, 18 noise calls per pixel — keep it cheap, it runs for every sky pixel) drawing the horizon→zenith gradient, sun/moon, stars and fBm clouds that drift with `uTime`. `applyLight()` feeds it `uHorizon` (= `scene.background`, so fog and horizon match), `uZenith`, `uNight`, `uRain` (rain raises cloud cover and greys them).
   **Pond water**: `M.water` is a `MeshStandardNodeMaterial` with TSL `normalNode`/`colorNode` (uniforms in `waterU`): a wave height field `wH` plus rain rings `wRings` perturbs the normal and tints the colour on the top face (`positionWorld.y>0.22` — keep in sync with the pond height); lighting, shadows and fog stay three.js's.
6. **Render loop** (`setAnimationLoop`): eases `blend`/`rainB`, steps animals with a shared clamped `dt`, animates rain, updates controls, renders.

**Cherry trees** (`sakura()`): trunk + a recursive `branch()` (5 limbs → 3 branches → 2 twigs each) merged into one mesh (`mergeGeometries`, `M.sakuraBark`). Each branch is a `CatmullRomCurve3` bent by `vnoise` (smooth 3D value noise, deterministic) and sagging under gravity (`y -= a·t²`, `a` grows with length² and horizontality); children branch off at golden-angle (`GOLD` ≈ 137.5°) azimuths with an upward bias. Dense core spheres (`M.sakuraCore`) and one hand-built `BufferGeometry` of blossom cards — alpha-tested quads textured with `T.blossom` (five-petal flowers on a transparent canvas) — sit at the branch/twig ends as Fibonacci spheres (golden-angle spiral, no grid lines or gaps), plus single blossoms spiralling along each twig. Each limb gets a pink `tint` that its children inherit with jitter; `card()` shifts it by altitude (paler on top) and depth (twig tips pinker). Each card is indexed for both windings with the same outward-pointing normal (so the crown shades like a volume, not like random cards) and carries a vertex colour (paler/pinker, darker inside and below). It uses its own generator `srnd` so tree placement via `rnd` is unaffected. **Wind:** `sway()` sets the TSL `swayPos` as `positionNode` on `M.sakura`/`M.sakuraCore`/`M.sakuraBark` (node materials; uniforms in `windU`, set in the render loop; `uGust` rises with `rainB`): a storm: the crown stays bent downwind and sways with gusts (`g`, travelling across the scene in wind direction), growing with (height above 1)², plus fast position-dependent branch whipping, both functions of object coordinates so blossoms stay on their twigs. The renderer's shadow pass reuses a material's `positionNode` (and the map alpha with `alphaTest`), so the shadows sway too — use `sway()` on any new cherry-tree material.

**Pine trees** (`pine()`, after `sakura()` because it uses `vnoise`/`nHash`): a tapered trunk bent by a lean plus `vnoise` (`bend(y)`), carrying 4–7 needle tiers. Each tier is a `ConeGeometry` whose mantle is bulged by two octaves of `vnoise` and whose rim sags, shifted, tilted and rotated at random; all tiers are merged into one mesh with vertex colours (per-tree brightness and warm/cool shift, darker low and inside) on `M.leaf`.

There are four random generators: `srnd` (cherry trees, seed 3), `prnd` (pines, seed 5), `trnd` (textures, seed 11) and `rnd` (scenery/tree placement and deer spots, seed 7, declared in the trees section). `rnd` is used by code that runs after its declaration — don't call it earlier.
